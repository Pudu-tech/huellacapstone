## Priorización propuesta

Primero se cierran las decisiones que condicionan desarrollo: ticket de salida, reportes mínimos, recordatorios y permisos de seguimiento. Después se integran y verifican los flujos comprometidos. En paralelo se resuelven documentación y evidencias académicas. La prioridad específica de cada issue debe ratificarse con el Product Owner y no se deduce solo de su número.

## Regla de actualización

Cada ítem debe tener necesidad o requisito, responsable, criterios de aceptación, dependencia, versión y evidencia. Una tarea cerrada sin evidencia se registra como revisión pendiente; una tarea abierta con código disponible se mantiene abierta hasta comprobar el criterio faltante. Los cambios al alcance pasan por el Plan de cambios.

## Control del snapshot

La planilla no modifica GitHub ni copia fechas tentativas como si fueran una nueva línea base. Es necesario reconciliar sus datos con GitHub Project, especialmente asignados, milestones y fechas, antes de publicar la planificación actualizada.
